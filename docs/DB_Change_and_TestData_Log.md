Row counts and widths, and therefore the size measurements, are not affected. The generator was fixed (v2: independent multiplicative hashes) and dry-run validated on sequences 17,901-21,900 (all 300 agents, 12 carriers, 8 underwriters used; wholesalers 30.0%; 6,721 paid / 1,115 partial / 3,364 unpaid; all seven checks passed, including the partial-payment check). The v1 rows are still in the database. See the open decision in the assessment.

* Measured: about **3.0 MB per 1,000 invoices**, which is about 2.94 GiB per 1M invoices. The pre-load estimate was 4.4 GB per 1M (the measurement is about 33% lower, inside the stated ±40%). The difference comes mostly from fewer payment-application line items per invoice (1.64 measured, 3.5 assumed).
* Transaction log: 270 MB used of 384 MB (SIMPLE recovery, 2,000-policy batches).
* Load speed: about 1,550 invoices per second (32.5 s for 50,120 invoices).
* **Projection (an extrapolation, not a measurement):** the 5M-invoice target would need about 15 GB of data, which exceeds the 10 GB Express cap regardless. A budget of 8.5 GB (85% of the cap) allows about 2.9M invoices; **2.5M invoices (about 7.4 GB) is the recommended target**, leaving about 2.6 GB for index rebuilds and free space. Estimated reload/extension time: about 27 minutes.
* Finding to verify (functional, not performance): `Seq_Accounting_GenerateInvoiceNo` is one global sequence and the application builds the number as `'INV' + RIGHT('000000' + seq, 6)`. Above 999,999 the number wraps and repeats, so a load of 2.5M invoices will contain duplicate `InvoiceNo` values, exactly as the application would produce.

Verified after apply (change #3): LIC ids 2000-2010; the orphan `LineItems_Directions` rows (2,528) are untouched; `USP_Accounting_GetLineItems_ClientsByBillingType_Id` returns 8, 7 and 5 distinct line items for billing types 1, 2 and 3, as designed.

Changes made by the user during the reload (not by Claude), observed read-only:
* `Seq_Accounting_GenerateInvoiceNo` restarted at 1 while the reload was running (batch 1-319,200 invoices were numbered from INV011310 upward; invoices after the restart are numbered from INV000001), so the two ranges overlap and about 319,000 invoice numbers appear twice. `USP_Accounting_GenerateInvoiceNo` itself is unchanged (still `RIGHT('000000' + seq, 6)`), so numbers also wrap after 999,999. No unique constraint exists on `InvoiceNo`, so nothing failed; it only matters if a test filters or joins by invoice number.
* `Accounting_LU_ReportTemplates`: 3 rows inserted for client 1 and mapped to the right reports: Report 2 (Agency Billed - Account Statement), Report 3 (Direct Billed - Commission Statement) and Report 9 (Insured Billed - Commission Statement). Reports 12 (Agency Detailed), 13 (Underwriter) and 15 (Direct/Insured Billed) have no template for this client.

Earlier inserts by the user (not by Claude): report configuration rows (17 reports, 14 output tables, 319 input-parameter rows, and related tables).

## Instance setting on MSSQLSERVER2022 (2026-11-12): how to revert
`max server memory (MB)` on the `MSSQLSERVER2022` instance was set to 12288 for the Standard-edition benchmark.

**To revert the cap:** run `EXEC sp_configure 'max server memory (MB)', 2147483647; RECONFIGURE;` on that instance. The old value was 2147483647, the default unlimited. `show advanced options` was already on, so it was not changed. Nothing else on the instance was touched.
